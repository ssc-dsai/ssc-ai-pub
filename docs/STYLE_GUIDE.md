# Style Guide

Conventions for writing and formatting publications on this site.

## Voice and tone

- Write in plain language; avoid jargon and unexplained acronyms.
- Prefer active voice and second person ("you") for guidance documents.
- Keep sentences short; aim for a grade 8-10 reading level in both languages.

## Structure

- Use a single `##` heading to introduce each major section; avoid skipping
  heading levels (don't jump from `##` to `####`).
- Lead with a one-paragraph summary of the takeaway before details.
- Use numbered lists for sequential steps and bullet lists for unordered
  items.

## Bilingual content

- English and French versions must cover the same content — not necessarily
  a literal word-for-word translation, but equivalent in scope and detail.
- Use Government of Canada terminology from [TERMIUM Plus](https://www.btb.termiumplus.gc.ca/)
  for technical and departmental terms.
- Dates: `15 November 2024` (EN) / `15 novembre 2024` (FR); the `readableDate`
  template filter formats this automatically from the `date` front matter
  field.

## Formatting

- Front matter `title` is plain text only (no Markdown, no trailing period).
- Use relative links for internal pages (`/en/publications/`) rather than
  absolute URLs, so links work across environments.
- Wrap acronyms on first use: "Algorithmic Impact Assessment (AIA)".
- Tables should have a header row and use Markdown pipe syntax.

## Accessibility

- Every image must have descriptive `alt` text.
- Don't rely on colour alone to convey meaning.
- Use meaningful link text (avoid "click here").
- Headings must be in logical order for screen readers.

## Tags

Always include the `publications` tag. Add one or more topic tags from the
existing set where possible (`guidance`, `research`, `generative-ai`,
`responsible-ai`, etc.) rather than inventing near-duplicate tags.

# Guide de style

Conventions de rédaction et de mise en forme des publications du site.

## Voix et ton

- Utiliser un langage clair; éviter le jargon et les acronymes non expliqués.
- Privilégier la voix active et la deuxième personne (« vous ») dans les
  documents d'orientation.
- Faire des phrases courtes; viser un niveau de lecture de la 8e à la 10e
  année dans les deux langues.

## Structure

- Utiliser un seul titre `##` pour introduire chaque section principale;
  éviter de sauter des niveaux de titre.
- Commencer par un paragraphe résumant le message principal avant les détails.
- Utiliser des listes numérotées pour les étapes successives et des listes à
  puces pour les éléments non ordonnés.

## Contenu bilingue

- Les versions anglaise et FR-CA doivent couvrir le même contenu; il n'est pas
  nécessaire qu'il s'agisse d'une traduction littérale, mais la portée et le
  niveau de détail doivent être équivalents.
- Utiliser la terminologie du gouvernement du Canada provenant de
  [TERMIUM Plus](https://www.btb.termiumplus.gc.ca/) pour les termes
  techniques et ministériels.
- Dates : `15 November 2024` (EN) / `15 novembre 2024` (FR-CA); le filtre de
  gabarit `readableDate` les formate automatiquement à partir du champ
  `date` des métadonnées.

## Mise en forme

- Le champ `title` des métadonnées doit être en texte brut, sans Markdown ni
  point final.
- Utiliser des liens relatifs pour les pages internes (`/fr/publications/`)
  plutôt que des URL absolues afin que les liens fonctionnent dans tous les
  environnements.
- Développer les acronymes à leur première occurrence : « évaluation de
  l'incidence algorithmique (EIA) ».
- Les tableaux doivent comporter une ligne d'en-tête et utiliser la syntaxe
  Markdown avec des barres verticales.

## Accessibilité

- Chaque image doit avoir un texte `alt` descriptif.
- Ne pas utiliser la couleur seule pour transmettre une information.
- Utiliser un texte de lien significatif; éviter « cliquez ici ».
- Les titres doivent suivre une hiérarchie logique pour les lecteurs d'écran.

## Étiquettes

Toujours inclure l'étiquette `publications`. Ajouter une ou plusieurs
étiquettes thématiques existantes (`guidance`, `research`, `generative-ai`,
`responsible-ai`, etc.) plutôt que de créer des variantes presque identiques.
